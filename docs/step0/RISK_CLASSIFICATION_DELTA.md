## 2. 新增操作的定档

| 操作 | 档 | 沙箱 | 涉及资源 | 理由 |
|---|---|---|---|---|
| 读源模型 + 计算基线哈希 | **R0** | 无 | `model:read` | 纯只读，且哈希是"原模型未被修改"的证据来源 |
| 下载校准/评测数据集到本地缓存 | **R2** | 容器级 | `network:egress`、`disk:write`、`state:write` | 出网 + 写共享缓存目录 |

| 量化计算（PTQ） | **R2** | 容器级 | `gpu:write`（长时间）、`disk:write`、`model:read` | 主操作。产新目录，源目录只读挂载 |
| 精度对比（parity-check） | **R2** | 容器级 | `gpu:write`、`model:read` | 需要加载两份模型跑推理 |
| 性能对比（perf-validation） | **R2** | 容器级 | `gpu:write` | 同上，且**会临时占用端口**（要起两个端点）→ 实际会调用 serving 的 deploy |
| 写量化矩阵并标记 `verified` | **R1** | 进程级 | `state:write` | 只写自有状态文件 |
| 回退（删除产出、还原矩阵标记） | **R2** | 容器级 | `disk:write`、`state:write`、`gpu:write` | 删目录属破坏性；沿用 serving 的"只删自己登记的载体"原则 |
| 产出目录的哈希校验（对比源） | **R0** | 无 | `model:read` | 只读 |
| **执行 QAT** | **R3** | **VM 级** | `gpu:write`、`disk:write`、`model:read` | **本机不可用 → 拒绝**，见 §5 |
| 装量化工具链（构建镜像） | **R2** | 容器级 | `network:egress`、`disk:write` | 构建专用镜像；不写入宿主 Python 环境 |
| 修改源模型文件 | **R6** | — | — | **一律拒绝**（题面"原始模型只读"） |
| 提权 / 动宿主服务 / 改内核 | **R6** | — | — | 沿用基线 |

## 3. 新增的安全门禁（量化特有）

这三条是本插件**区别于 serving 的核心安全属性**，每一条都必须有独立的失败码与可复核证据。

### 3.1 去泄漏门禁（强制，不可关闭）

**判据不是"索引不重叠"，而是内容哈希交集为空。**

```
切分：dataset(split) → 按内容 sha256 去重 → 按种子随机切 校准段 / 测试段
校验：sha256(校准段所有条目) ∩ sha256(测试段所有条目) == ∅
      且 两段并集 == 去重后的全集（不丢样本）
失败 → E_CALIB_LEAKAGE_DETECTED，立即中止，不进入量化
```

**为什么按内容哈希**：同一段文本可能同时出现在 `train` 与 `test` 两个 split（很多数据集确实如此），按索引判断会漏。这是**可证伪**的判据 —— 交集为空可以逐条复核。

**血缘落盘**（写进量化矩阵，使门禁事后可复核）：
来源 URL + 数据集 revision sha + 切分种子 + 去重后条目数 + 两段哈希清单的 sha256。

### 3.2 原始模型只读 + 哈希校验

```
量化前：srcHashBefore = 递归 sha256(源模型目录, 排除 mtime/权限)
量化后：srcHashAfter  = 同一算法再算一次
断言：srcHashBefore == srcHashAfter
失败 → E_SOURCE_MODEL_MODIFIED，中止并告警
产出目录约束：必须与源目录同名不同路径，且不得位于源目录内部
```

### 3.3 精度门禁独立（量化不得自签精度）

**实现约束**：量化模块**不得**自己判"精度够不够"。它只能：

1. 调用精度评估（testing-core 契约实现）拿到数值；
2. 把数值与**调用方传入的容忍阈值**比较；
3. 两者的来源在报告里分开标注（`measured.accuracy` vs `threshold.accuracy`）。

`[inferred]`（依据：题面"精度门禁独立：量化不能自己签收精度"）：这意味着**阈值必须由外部传入**，不能在插件内硬编码一套"默认够好"的标准 —— 否则"独立"就名存实亡。

## 5. 关于 QAT 的建议（需要你裁决）

题面把 QAT 列为降级链的最后一档。DSH 建议 **把它实现为"可规划的终态"而非自动执行的一档**，理由三条：

1. **风险档跳变**：QAT 是训练，写的是新权重、跑数小时、占满 GPU。在已确认的分级里它落在 **R3**（需 VM 级沙箱），而**本机没有 VM 级沙箱** → 按已确认的处置（`refuse`）它必然被拒绝。这是**规则自洽的结果**，不是实现偷懒。
2. **人工决策点已经覆盖了它**：你给的清单里有一条"所有降级方案精度均不达标 → 选择 **QAT** / 放宽阈值 / 回退"。也就是说 QAT 本就应该是**人来选**的分支，而不是自动降级链的一环。
3. **自动与人工混在一起会破坏"降级链有界"**：QAT 的耗时（小时级）与 PTQ 的降级档（分钟级）不在一个量级，"最多 5 级"的预算对它是无意义的。

**因此建议**：降级链实现为 `INT4 → INT8 → FP8 → W8A16 →（第 5 档：QAT 规划）→ 回退`，
其中第 5 档的动作是**产出一份 QAT 计划并停下等你裁决**（`E_QAT_REQUIRES_APPROVAL`），而不是启动训练。
若你希望它真跑，需要显式授权把 R3 降级到容器级 —— 那是一条**单独确认**的路径。

## 6. 人工决策点（在 serving 清单上的追加）

| 场景 | 动作 | 档位 |
|---|---|---|
| 校准集与测试集有交集 | **中止**（`E_CALIB_LEAKAGE_DETECTED`），不询问 —— 这是硬门禁 | R6 语义 |
| 所有降级方案精度均不达标 | 停下，给三个选项：**QAT** / 放宽阈值 / 回退 | R3（QAT）/ R2 |
| 精度损失接近容忍上限（如已达阈值的 90%） | 停下确认是否继续 | R2 |
| 量化签收后影响生产 | 停下确认 | R5 |
| 源模型哈希在量化前后不一致 | **中止并告警**（按 3.2） | R6 语义 |
| 需构建新镜像（装量化工具链） | 先报告再执行（系统级影响面：磁盘 + 网络） | R2 |
| 数据集来源 license 不明确 | 停下确认（沿用 serving 的 license 门禁） | R2 |
